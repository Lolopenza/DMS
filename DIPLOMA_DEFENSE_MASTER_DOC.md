# DIPLOMA_DEFENSE_MASTER_DOC

**Название проекта:** веб-платформа DMC (Discrete Math Calculator) с ИИ-компонентом для формирования математических навыков.

**Назначение документа:** комплексный аудит текущего состояния, оценка готовности к защите диплома и структурированный материал для презентации и устной речи.

**Источники контекста:** анализ кодовой базы (март 2026), файл [REVIEWS.md](./REVIEWS.md) (архитектурный обзор и дорожная карта до внедрения фаз 1–3). Папка `docs/` в репозитории на момент подготовки документа не содержала файлов.

## Раздел 1. Аудит системы и обзор прогресса

### 1.1. Краткое резюме: дельта «старая архитектура → текущее состояние»

| Область | Было (по REVIEWS.md / ранний MVP) | Стало (после фаз 1–3) |
|--------|-----------------------------------|------------------------|
| **Связь Frontend ↔ Math Engine** | Прямые вызовы движка, обход бэкенда; риск обхода аутентификации | Паттерн **API Gateway на Spring Boot**: `CalculatorController` + `CalculatorProxyService` → `MathEngineClient` с заголовком **`X-Internal-Api-Key`**; запись в `calc_history` для аутентифицированных пользователей |
| **Защита Math Engine** | Публичные эндпоинты, CORS `*` | Проверка внутреннего ключа в FastAPI (`INTERNAL_API_KEY` / `DMC_MATH_ENGINE_API_KEY`) при ненулевом и не дефолтном значении |
| **Инфраструктура** | Замечания по портам RabbitMQ, отсутствию лимитов ресурсов | В `docker-compose.override.yml` заданы **`mem_limit` и `cpus`** для сервисов |
| **Надёжность и диагностика** | «Тихое» глотание исключений, отсутствие логов в generic handler | В `GlobalExceptionHandler` — структурированное логирование (`log.warn` / `log.error` с исключением) |
| **Зависимости бэкенда** | Неиспользуемые starter’ы (WebFlux, AMQP и др.) | Упрощённый `pom.xml`: оставлены актуальные стартеры; **HttpClient** (Java 11+) для вызова math engine |
| **Образовательный домен** | Схема БД без полноценного JPA/REST для курсов и задач | **CRUD курсов/уроков** (`LearningController`), роль **`TEACHER`**, таксономия **topics**, шаблоны задач, попытки по статическим задачам |
| **ИИ и генерация** | Идея в roadmap | Вертикальный срез: таблицы **`generated_problems`** / **`generated_problem_attempts`** (JSONB-снимок состояния), эндпоинты **`/api/problems/generated`**, гибридная верификация в Python |

**Итог дельты:** платформа эволюционировала от «калькулятор + авторизация» к **многослойной образовательной системе** с **контролируемым межсервисным доступом** и **доказуемым ИИ-слоем** (генерация + проверка ответов).

### 1.2. Глубокий аудит подсистем

#### 1.2.1. Frontend (React 18 / Vite / Tailwind)

**Сильные стороны**

- Богатая предметная часть: множество модулей по дискретной математике и смежным разделам (наследие MVP).
- Реализован **минимально достаточный UI** для дипломного сценария ИИ: страница интерактивной практики (`InteractivePractice.jsx`) — выбор темы, сложности, режима (**AI / TEMPLATE**), генерация, отправка ответа, список недавних сгенерированных задач.
- API-обёртки для бэкенда: `generateInteractiveProblem`, `listMyGeneratedProblems`, `submitGeneratedProblemAttempt` в `api.js`.
- Чат с движком через прокси: `Chatbot.jsx` → `/api/calculator/chat` (согласуется с gateway на бэкенде).

**Пробелы относительно «идеального» дипломного фронтенда**

- **Визуализация прогресса и аналитика:** нет дашбордов мастерства, графиков, отчётов для комиссии (в roadmap — Feature 4).
- **Педагогический UX:** нет пошаговых подсказок с уровнями (scaffolding), очереди повторений (spaced repetition), адаптивного подбора следующей задачи (BKT).
- **Качество инженерии UI:** возможны пустые `catch`, отсутствие таймаутов `fetch` (замечание из REVIEWS.md частично актуально), нет полноценных E2E-тестов (Playwright/Cypress).
- **Единообразие доступа к токенам:** если где-то сохраняется JWT в `localStorage`, это остаётся **точкой для вопросов по XSS** на защите — лучше опереться на HttpOnly cookies там, где это уже поддержано бэкендом.

**Что имеет смысл «быстро подтянуть» перед защитой**

1. Одна-две **демонстрационные** страницы: краткая «лента» последних попыток с фильтром по теме; визуальное отображение `verification_method` и `confidence` после отправки ответа.
2. **Скелетоны загрузки** и явные сообщения об ошибках сети/таймаутов.
3. Слайды/скриншоты, показывающие **полный пользовательский сценарий** от входа до проверки ответа ИИ.

---

#### 1.2.2. Backend (Spring Boot 3.2, Java 21)

**Сильные стороны**

- **Аутентификация и сессии:** сильная база для MVP (ротация refresh-токенов, детект повторного использования, BCrypt, блокировка аккаунта и др. — см. REVIEWS.md).
- **Gateway к Math Engine:** `MathEngineClient` передаёт **`X-Internal-Api-Key`**, задаёт таймаут HTTP-запроса; ошибки движка маппятся в `ApiException` с кодами вроде `MATH_ENGINE_ERROR` / `MATH_ENGINE_UNAVAILABLE`.
- **Предметная область:** `LearningController` с разграничением **ADMIN / TEACHER** для мутаций; `ProblemController` — задачи, топики, шаблоны, генерация из шаблона, **интерактивная генерация** и попытки по `generated_problems`.
- **Миграции Flyway:** в т.ч. `V12` (роль TEACHER, топики, шаблоны), `V13` (generated problems + attempts).
- **Тесты:** появились интеграционные и модульные тесты (auth, learning, problems, calculator) — это **существенный плюс** для диплома по сравнению с формулировкой «тестов нет» в раннем AGENTS.md.

**Пробелы и риски**

- **Redis** подключён зависимостью, но **кэширование, rate limiting и blacklist JWT** могут быть ещё не реализованы — комиссия может спросить про отзыв access-токена и защиту от перегруза.
- **RabbitMQ** в стеке может оставаться без бизнес-логики — обосновать как «инфраструктура под асинхронные задачи следующих этапов» или сократить в дипломном тексте акцент на нём.
- **Анонимный** прокси для `/api/calculator/chat` (`proxyAnonymous`) — осознанный компромисс для UX; на защите нужна **чёткая формулировка** политики (лимиты, злоупотребления, отключение в проде).
- **CSRF, rate limiting на `/api/auth/*`** — темы из REVIEWS.md остаются релевантными для вопросов безопасности.

**Что имеет смысл быстро усилить**

1. Краткое описание в пояснительной записке: **поток данных** от клиента до math engine и обратно, таблица ролей.
2. При возможности — **базовый rate limit** на дорогие эндпоинты (генерация/верификация) или документирование планов.
3. Проверка, что SpringDoc/OpenAPI отражает новые контроллеры — удобно для приложения к диплому.

---

#### 1.2.3. Math Engine и ИИ (FastAPI, Python, SymPy, Gemini)

**Сильные стороны**

- **Гибридная верификация** (`problem_generation.py`, эндпоинт `/verify`):
  - **Символьный путь:** SymPy — `simplify(expected - candidate) == 0` при наличии `answerExpression`, `operation`, `params` — воспроизводимость и научная строгость.
  - **Семантический путь:** LLM-судья (Gemini) возвращает JSON `correct`, `confidence`, `feedback`.
  - **Резерв:** сравнение строк при сбоях ИИ, если известен `expectedAnswer`.
- **Генерация** (`/generate`): промпт с требованием строгого JSON; подстановка параметров в выражение и **проверка вычислимости** через SymPy; fallback при ошибках LLM или парсинга.
- **Тестовое покрытие** math engine (исторически ~88 тестов) — аргумент в пользу зрелости вычислительного ядра.
- **Защита внутреннего API** при корректной конфигурации ключа.

**Пробелы и риски**

- **Галлюцинации и смещение LLM** при генерации формулировок и при семантической проверке — на защите обязателен честный ответ: символьный слой снижает риск для класса задач, но не устраняет его полностью для открытых ответов.
- **Стоимость и лимиты API** Gemini — нет в явном виде в пользовательском UI (метрики токенов в БД для чата из REVIEWS.md всё ещё актуальны как улучшение).
- **RAG:** в обзоре указан прототип с ограниченным индексом; полноценный векторный индекс (pgvector/Qdrant) — за рамками текущего среза, но усилил бы «научность» ИИ-части.
- **Ошибки по подстрокам** в чате (`'429' in err`) — известный техдолг из REVIEWS.md; для диплома лучше упомянуть как направление рефакторинга.

**Что имеет смысл быстро усилить**

1. В пояснительной записке — **блок-схема** решения: когда вызывается SymPy, когда LLM.
2. 1–2 **примера** в приложении: задача → символьный ответ → проверка; задача с нестандартной записью ответа → семантическая проверка.
3. Формулировка **ограничений применимости** метода (классы задач, этика, безопасность промптов).

## Раздел 2. Оценка готовности к защите диплома

### 2.1. Достаточно ли текущего состояния для бакалавриата / магистратуры?

**Тема:** «Разработка веб-платформы с использованием системы ИИ для формирования математических навыков».

| Уровень | Оценка | Обоснование |
|---------|--------|-------------|
| **Бакалавриат** | **В целом достаточно**, при условии качественного текстового оформления | Есть полноценный **стек**, **безопасный контур** вызова вычислений, **предметная модель** (курсы, уроки, роли, задачи), **новизна** — гибридная верификация и генерация задач с сохранением снимка в JSONB. Это выходит за рамки «учебного CRUD». |
| **Магистратура** | **Пограничное / требует усиления теоретической части** | Комиссия ожидает **метрики**, **эксперимент**, **сравнение с baseline** (только SymPy vs SymPy+LLM, качество подсказок, педагогический эффект). Нужны разделы: постановка эксперимента, критерии качества, ограничения ИИ, этика и воспроизводимость. |

**Вывод:** для **бакалавра** проект выглядит **защищаемым** как инженерная работа с элементами ИИ. Для **магистра** желательно добавить **исследовательский слой** (даже на небольшой выборке пользователей или synthetic benchmark).

### 2.2. Критические слабые места и линии обороны

| Возможная атака комиссии | Как отбить / что быстро исправить |
|--------------------------|-----------------------------------|
| «Это обычный CRUD + вызов ChatGPT» | Подчеркнуть **гибридную верификацию**, **нормализованные сущности** (topics, templates), **gateway с ключом**, **аудит calc_history**, **два режима генерации** (AI vs шаблон). |
| «ИИ проверяет ответы ненадёжно» | Согласиться частично: **для структурированных ответов приоритет SymPy**; LLM — для семантики и обратной связи; указать **confidence** и **method** в ответе верификации. |
| «Безопасность: XSS, JWT, CSRF» | Описать текущую модель (cookies vs localStorage), план **CSRF** и **rate limit**; не преувеличивать — честно назвать статус «в планах / частично». |
| «Нет педагогической адаптации (BKT, ZPD)» | Сослаться на REVIEWS.md как на **дорожную карту**; показать, что **уже есть** skill level, difficulty, topic taxonomy — фундамент для адаптации. |
| «Нет доказательства, что обучение улучшается» | Предложить **качественную оценку** (опрос), **количественные** метрики (доля верных с первой попытки до/после подсказок) — хотя бы на демо-данных. |
| «Redis/RabbitMQ не используются» | Позиционировать как **готовность инфраструктуры** к масштабированию и асинхронным заданиям; не выдавать за реализованный функционал. |

## Раздел 3. Шпаргалка для презентации и речи

### 3.1. Продукт: elevator pitch (30–40 секунд)

> **DMC** — это веб-платформа для изучения дискретной математики, объединяющая классические вычислительные модули, структурированные курсы и задачи с **генерацией под пользователя**. Система не просто выдаёт ответ: она **строит задачу**, сохраняет её параметры и эталон, а при проверке ответа **сочетает символьную математику (SymPy) и семантический анализ (Gemini)** — так мы балансируем строгость и гибкость при обучении.

---

### 3.2. «Убийственные» особенности (для 2–3 слайдов)

1. **ИИ-генерация задач с снимком состояния**  
   Каждая сгенерированная задача фиксируется в БД (**JSONB**): формулировка, параметры, выражение для ответа, режим генерации, связь с шаблоном. Это позволяет **воспроизводить проверку** и вести статистику попыток.

2. **Гибридная проверка (Hybrid Grading)**  
   Сначала **детерминированная** проверка через SymPy; при невозможности — **LLM-судья** с уровнем уверенности и текстовой обратной связью; при сбоях — контролируемый fallback.

3. **Защищённая архитектура вызова движка (Gateway)**  
   Браузер обращается к **Spring Boot**; бэкенд подставляет **секретный ключ** и вызывает Python-сервис. Так вычисления и ИИ **не являются полностью публичным API** для произвольного клиента.

4. **Роли и контент**  
   Роль **TEACHER** (совместно с ADMIN) для создания топиков и шаблонов — связь с реальной моделью «преподаватель — студент».

### 3.4. Поток данных (устное описание для слайда «Архитектура»)

1. Пользователь в **браузере** открывает SPA (в проде статика через **Nginx**).
2. Запросы к домену API идут на **Nginx**, который проксирует, например, `/api/*` на **Spring Boot (8080)**.
3. **Spring Security** проверяет JWT / сессию; контроллеры **Learning** / **Problems** / **Calculator** выполняют бизнес-логику.
4. Для вычислений и ИИ бэкенд вызывает **Math Engine (8081)** по HTTP JSON, добавляя **`X-Internal-Api-Key`**.
5. Math Engine выполняет **SymPy** или обращается к **Gemini**; результат сериализуется в JSON.
6. Ответ возвращается в Spring Boot (при необходимости пишется **история**), затем клиенту; UI обновляет состояние (задача, результат проверки, список истории).

*Кратко для речи:* «Один вход через API-шлюз на Java, секрет между Java и Python, два уровня проверки ответа — символика и ИИ.»

---

### 3.5. Академическая ценность (почему это не «просто сайт»)

- **Методологически:** сочетание **формальной верификации** (компьютерная алгебра) и **NLP/LLM** для обучения отражает современную практику **intelligent tutoring** и **AI in education**.
- **Инженерно:** классический **микросервисный** паттерн с **явной границей доверия** (internal API key), **версионируемой схемой БД** и **аудитом** вычислений.
- **Предметно:** дискретная математика как область, где символьные методы особенно уместны — тема диплома **согласована** с выбором инструментов.
- **Для развития:** в проекте заложены направления, описанные в REVIEWS.md (BKT, аналитика, RAG, spaced repetition) — их можно озвучить как **научно-исследовательский задел**.

9. Генерация: AI vs шаблон.  
10. Гибридная проверка: блок-схема SymPy → LLM → fallback.

### 3.7. Фразы-заготовки для ответов на типовые вопросы

- **Почему два языка (Java и Python)?**  
  Java — типовой выбор для **корпоративного** бэкенда, безопасности и интеграции с БД; Python — **экосистема** SymPy и ML/LLM. Разделение ответственности упрощает развитие вычислительного ядра.

- **Почему не только LLM?**  
  Символьная проверка **воспроизводима** и не зависит от «настроения» модели для алгебраических эквивалентностей.

- **Что если API Gemini недоступен?**  
  В верификации предусмотрены **fallback**-ветки; при генерации — **шаблонный** режим и заготовленные fallback-задачи.

- **Как вы защищаете Math Engine?**  
  **Внутренний ключ** на запросах от бэкенда; в публичной сети движок не должен быть доступен без межсетевого экрана.
